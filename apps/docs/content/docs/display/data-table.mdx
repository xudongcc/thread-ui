## API Style

`DataTable` uses a [props-first API](/docs/api-design/props-first). Pass row data,
column definitions, actions, and pagination behavior as configuration props.

## Installation

```bash
pnpm dlx shadcn@latest add @thread-ui/data-table
```

## Usage

```tsx
import {
  DataTable,
  type DataTableColumnProps,
} from "@/components/thread-ui/data-table";
```

```tsx
interface User {
  id: string;
  name: string;
  email: string;
}

const columns: Array<DataTableColumnProps<User>> = [
  {
    id: "name",
    header: "Name",
    field: "name",
  },
  {
    id: "email",
    header: "Email",
    field: "email",
  },
];

const data: Array<User> = [
  { id: "1", name: "Alice", email: "alice@example.com" },
  { id: "2", name: "Bob", email: "bob@example.com" },
];

<DataTable columns={columns} data={data} />;
```

## Localization

`DataTable` reads its built-in empty state, selection controls, row action trigger labels, and pagination labels from `AppProvider`. Register the `thread-ui` namespace on your i18next instance and pass that instance to `AppProvider`.

## Examples

### Row Selection

Enable row selection with `onRowSelectionChange` and display bulk actions when rows are selected.

Selection belongs to the supplied `data`. Updating data preserves selected IDs
that still exist and removes IDs that are no longer present; returning to an old
page does not restore its selection. Use stable record IDs or `getRowId` when
reordering, filtering, or paginating records.

`onAllRowsSelectedChange` reports the explicit “Select all” mode. Unchecking a row,
clearing the header checkbox, or changing data so the selection is no longer valid
exits that mode and reports `false`. It does not load or retain records across pages.

### Column Types

<Preview path="data-table-types" />

| Type             | Default alignment | Options                                    |
| ---------------- | ----------------- | ------------------------------------------ |
| `text` (default) | Left              | Common column props only                   |
| `number`         | Right             | `locale`, `precision`                      |
| `currency`       | Right             | `locale`, `precision`, required `currency` |
| `percent`        | Right             | `locale`, `precision`                      |
| `date`           | Left              | `locale`, `timeZone`                       |
| `datetime`       | Left              | `locale`, `timeZone`                       |
| `time`           | Left              | `locale`, `timeZone`, `hour12`             |
| `duration`       | Right             | `locale`, `unit`, `style`                  |

```tsx
<DataTable
  locale="en-US"
  timeZone="Asia/Shanghai"
  columns={[
    { field: "name", header: "Name" },
    { field: "total", header: "Total", type: "currency", currency: "USD" },
    { field: "rate", header: "Rate", type: "percent", precision: 1 },
    {
      field: "elapsed",
      header: "Duration",
      type: "duration",
      unit: "seconds",
      style: "digital",
    },
    {
      field: "createdAt",
      header: "Created",
      type: "datetime",
      locale: "zh-CN",
      timeZone: "America/New_York",
    },
  ]}
  data={data}
/>
```

- **Locale:** column `locale` → table `locale` → runtime default locale (the user's
  browser locale on the client). This only affects formatted values; empty states, pagination, and other UI
  labels continue to use AppProvider. Text columns have no `locale` option.
- **Precision:** fixed fraction digits (0–100). Omit it to use `Intl.NumberFormat`
  defaults: up to 3 decimal places for numbers, the currency's minor-unit digits
  for amounts, and 0 decimal places for percentages.
- **Currency:** specify an ISO 4217 code such as `USD`, `CNY`, or `JPY`. Values are
  in major units (`12.5` means $12.50 for USD), not cents. Locale never implies a currency.
- **Percent:** supply a ratio; `0.125` with `precision: 1` displays as `12.5%`.
- **Dates:** accept `Date`, epoch milliseconds, `YYYY-MM-DD`, or ISO timestamps
  with an explicit `Z` / UTC offset. `date` displays year/month/day; `datetime`
  also displays hours/minutes/seconds using the locale's clock convention.
  Time zone priority is column `timeZone` → table `timeZone` → runtime default
  time zone (the user's browser time zone on the client). Date-only strings in a
  `date` column keep their calendar date regardless of `timeZone`.
  A date-only string in `datetime` or `time` is midnight UTC converted to the chosen zone.
- **Time:** `type: "time"` displays only hours/minutes/seconds and supports the same
  date inputs and locale/time-zone precedence. `hour12: true` selects a 12-hour
  clock; `false` selects a 24-hour clock; omit it to follow the locale. Bare time
  strings such as `13:04:05` remain plain text because they have no date or time
  zone; supply a timestamp to enable formatting and time-zone conversion.
- **Duration:** accepts a finite numeric elapsed time. `unit` is `milliseconds`,
  `seconds` (default), `minutes`, or `hours`. Values are rounded to the nearest
  millisecond, then split into hours, minutes, seconds, and milliseconds.
  Hours do not wrap at 24; negative values keep their sign. `style` supports
  `digital` (default), `long`, `short`, and `narrow`, using `Intl.DurationFormat`.
  For example, `3661` seconds displays as `1:01:01`; `long` with `en-US` displays
  `1 hour, 1 minute, 1 second`. Locale follows the usual column/table/runtime
  precedence. Durations have no `timeZone` and ignore the table's time zone.
  Values outside the safe integer millisecond range remain plain text.
  On runtimes without `Intl.DurationFormat`, the raw value remains visible;
  load a compatible polyfill before rendering if localized durations are needed.
- **Empty/invalid values:** `null` and `undefined` stay blank; zero remains visible.
  Numeric formatting accepts finite numbers and bigints; other values, invalid
  dates, and datetime strings without a UTC offset remain plain text. Invalid
  locale, currency, time zone, or precision configurations follow Intl's validation.

When server-rendering, pass the user's `locale` and `timeZone` explicitly to keep
server and browser output consistent. Unspecified Intl options use the server's
settings during SSR, which may differ from the browser's settings. AppProvider's
language controls UI translations, not the default formatting locale.

`render` and `align` can override defaults. Formatting changes only presentation;
row data and `getValue()` remain unformatted.

### Column Alignment

Set `align` to `"left"`, `"center"`, or `"right"` to align both the header and
cells. Numeric and duration types default to `"right"`; other types default to `"left"`.
An explicit `align` overrides the type default.

```tsx
const columns: DataTableColumnProps<User>[] = [
  { field: "name", header: "Name" },
  { field: "email", header: "Email", align: "center" },
  { field: "id", header: "ID", align: "right" },
];
```

Alignment applies to the outer `th` / `td`, including pinned columns. Custom
renderers that use their own flex or grid layout control their internal alignment.

## Features

- **Row Selection** - Single and multi-row selection with bulk actions support
- **Row Actions** - Dropdown menu with customizable actions per row
- **Column Pinning** - Pin columns to the left or right for better visibility
- **Pagination** - Built-in pagination controls
- **Row Click** - Handle row click events for navigation or detail views
- **Flexible Columns** - Thread UI column definitions with custom headers, cells, and accessors

### DataTableColumnProps

`DataTableColumnProps<TData, TValue>` is a discriminated union of
`DataTableTextColumnProps`, `DataTableNumberColumnProps`,
`DataTableCurrencyColumnProps`, `DataTablePercentColumnProps`,
`DataTableDateColumnProps`, `DataTableDateTimeColumnProps`,
`DataTableTimeColumnProps`, and `DataTableDurationColumnProps`.
Each extends `DataTableBaseColumnProps<TData, TValue>`. All types are exported and
remain independent of TanStack Table. `TValue` preserves the accessor and render
context's value type. Plain objects default to `unknown`; use the column helper
below to infer it from a field or computed accessor. Omitting `type` keeps existing
text-column behavior.

### Inferred column values

`createDataTableColumnHelper<TData>()` follows the accessor-helper pattern: pass a
field path or a function to `accessor`, and its raw value type is inferred in
`render` and `header`. The helper uses Thread UI's own types, not TanStack types.

```tsx
import {
  DataTable,
  createDataTableColumnHelper,
} from "@/components/thread-ui/data-table";

interface Product {
  id: string;
  price: number;
  customer?: { name: string };
}

const column = createDataTableColumnHelper<Product>();
const columns = column.columns([
  column.accessor("price", {
    type: "currency",
    currency: "USD",
    header: "Price",
  }),
  column.accessor("customer.name", {
    header: "Customer",
    render: (props, { getValue }) => (
      <span {...props}>{getValue()?.toUpperCase() ?? "Guest"}</span>
    ), // getValue(): string | undefined
  }),
  column.accessor((product) => product.price * 2, {
    id: "doublePrice",
    header: "Double price",
    render: (props, { getValue }) => (
      <span {...props}>{getValue().toFixed(2)}</span>
    ), // getValue(): number
  }),
]);

const products: Product[] = [{ id: "1", price: 12.5 }];
<DataTable columns={columns} data={products} />;
```

`accessor` requires an options object (use `{}` for a field with defaults).
Computed accessors require `id`; `field` and `getValue` cannot be replaced in the
options. Use `column.columns([...])` to combine columns with different value types.
It keeps the same array at runtime and normalizes its type to
`DataTableColumnProps<TData>[]` for the table; each callback is type-checked at its
`accessor` call. Existing plain objects and explicit `TValue` remain supported.

Field paths are checked in both the helper and plain column definitions. Nested
objects, numeric array indices (`items.0.name`), and tuple positions are supported.
Optional parents and potentially missing array entries infer `undefined`; nullable
leaf values retain `null`. Paths are limited to six segments to support recursive
row models without unbounded type expansion. Use a computed accessor for deeper
paths or dynamic access. Exported `DataTableField<TData>` and
`DataTableFieldValue<TData, TField>` are available for reusable field selectors.

### Custom cell and row contexts

Following [Base UI composition](https://base-ui.com/react/handbook/composition),
`render` accepts either a React element or `(props, state) => JSX`.
`header` accepts any ReactNode (including text and JSX), or the same render-function
signature. A header element supplies its own content: `header: <strong>Name</strong>`.
For render functions, always forward `props` (including the ref) to your root
element. The element form of cell/action `render` merges props automatically.
Custom components used there must forward those props and their ref.

Custom cell renders replace a content `span`. Header nodes render directly;
header functions render a custom content element. The outer `td` / `th` stays
owned by DataTable to preserve semantics and column pinning.
Without `render`, the column type formats the accessor value. A render function
takes precedence over formatting and receives the raw value through `getValue()`
(and the original text fallback in `props.children`). A render element receives
the formatted default children, preserving the Base UI element composition API.

`render` state contains `{ row, column, getValue }`; `header` callback state contains
`{ column }`. These state objects are not forwarded to DOM attributes.
`row`, including the row passed to `rowActions`, action callbacks, and `onRowClick`,
contains only `{ id, index, original }`. `onRowSelectionChange` receives the original
records. No TanStack instance or methods are exposed.

```tsx
const columns: DataTableColumnProps<User, string>[] = [
  {
    id: "contact",
    getValue: (user) => `${user.name} <${user.email}>`,
    header: "Contact",
    render: (props, { getValue }) => <strong {...props}>{getValue()}</strong>,
  },
];
```

`field` supports dotted object paths such as `customer.name`. If it is omitted,
`id` is used as the field unless `getValue` is provided. Column `getValue(record, index)`
computes the value and takes precedence over `field`; the render context’s
`getValue()` returns that computed value. Supply an explicit `id` for computed
columns. Column sizing and left/right pinning are supported; sorting, filtering,
and pagination of the input records remain the application's responsibility.

When migrating from the old inherited types, replace engine-specific calls such
as `row.getValue("name")` with `row.original.name`, or use `getValue()` inside a
cell. Custom headers no longer receive a table instance.

The cell `render` element keeps the default value, while the header element supplies
its own label:

```tsx
const columns: DataTableColumnProps<User>[] = [
  {
    field: "name",
    header: <em>Name</em>,
    render: <strong />,
  },
];
```

Row action `render` replaces the menu item and supports framework Link components.
Its callback receives `(props, { row, disabled, highlighted })`. Forward `props` to
preserve keyboard interaction, disabled state, menu semantics, and action handlers.

```tsx
<DataTable
  columns={columns}
  data={data}
  rowActions={(row) => [
    { label: "View profile", render: <Link href={`/users/${row.id}`} /> },
  ]}
/>
```

Replace `cell: (context) => ...` with `render: (props, context) => ...`, forwarding
`props` to the returned element. Header callbacks use `(props, { column })`:

```tsx
header: (props, { column }) => <strong {...props}>{column.id}</strong>;
```

The separate `headerRender` option has been removed. Move it to `header`; when
using a JSX element, include the label as its children.

Rename legacy column options `accessorKey` to `field` and `accessorFn` to `getValue`.
