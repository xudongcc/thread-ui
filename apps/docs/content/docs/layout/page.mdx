## API Style

`Page` supports both Props and composition APIs. Use header props for standard
pages; compose the existing subcomponents when you need a custom header.
Both APIs share the same responsive layout and action behavior.

## Installation

```bash
pnpm dlx shadcn@latest add @thread-ui/page
```

## Props API

```tsx
import Link from "next/link";
import { Page } from "@/components/thread-ui/page";
import { Card } from "@/components/ui/card";

<Page
  title="Project settings"
  description="Manage your project and team."
  breadcrumbActions={[
    { label: "Projects", render: <Link href="/projects" /> },
    { label: "Thread UI", render: <Link href="/projects/thread" /> },
  ]}
  primaryAction={{ label: "Save", loading: saving, onAction: handleSave }}
  secondaryActions={[
    { label: "Duplicate", onAction: handleDuplicate },
    { label: "Delete", destructive: true, onAction: handleDelete },
  ]}
  paginationActions={{
    previous: { disabled: !hasPrevious, onAction: goPrevious },
    next: { render: <Link href="/projects/next" /> },
  }}
>
  <Card>{/* Page content */}</Card>
</Page>;
```

`title` and `description` accept `ReactNode`, including inline JSX. The root
`title` prop is the visible page heading, not a native div tooltip attribute.
Providing any header prop enables the Props API: Page generates `PageHeader`
and wraps `children` in `PageContent`. Empty action arrays do not render empty
menus. With no header props, children are rendered directly for composition.
Do not put `PageHeader` or `PageContent` inside a Page configured with header props.

Action configurations use `label` and `onAction`. Primary actions also support
`icon`, `loading`, `type="submit"`, and `form`; secondary actions support `icon`,
`destructive`, and `loading`. Optional `key` values give breadcrumb and secondary
actions stable identity when their lists change. The Page controls button sizes
and variants.

All action types support Base UI `render` as an element or render function.
Use it to supply your framework's Link; functions must forward the provided
props and ref. `paginationActions.previous` and `.next` each accept `render`.
Secondary links keep their destinations and disabled behavior when moved into
an overflow menu. Set `nativeButton` when a custom render returns a native button.
Loading secondary actions are disabled in both inline and menu presentations.

Built-in navigation and menu labels remain localized. Override action labels
with `aria-label`, or use composition for container-level label customization.

```tsx
<Page>

        Pet accessories
      </BreadcrumbAction>
    </BreadcrumbActions>

      <PagePrimaryAction>Save</PagePrimaryAction>
    </PageActions>
  </PageHeader>
  <PageContent>{/* Page content */}</PageContent>
</Page>
```

## Best Practices

Choose a variant based on the page's content and primary task rather than the
viewport size. `Page` already fills the available width until it reaches the
selected maximum width.

`Page` renders an outer wrapper with `p-4` and an inner, centered content
container. Width variants apply to the inner container: `compact` allows 42rem
(672px) of content, `default` allows 64rem (1024px), and `full` has no maximum.
The wrapper's 16px padding on each side is outside those limits. A compact Page
therefore reaches the `@2xl/page` breakpoint when its parent provides at least
704px of width (with the default 16px root font size).

`className`, `ref`, and other div attributes target the inner content container,
which also owns `@container/page`. `PageHeader` and `PageContent` remain direct
children in the composition API.

| Variant   | Best suited for                                      | Avoid when                                      |
| --------- | ---------------------------------------------------- | ----------------------------------------------- |
| `default` | Detail pages, settings, editors, and most CRUD pages | The content is a single short, focused form     |
| `compact` | Focused forms, setup steps, confirmations, and flows | The page contains wide tables or dense panels   |
| `full`    | Dashboards, data tables, canvases, and split views   | Unconstrained text or a simple single-column UI |

### Prefer Default

Start with `default` for most product pages. Its `max-w-5xl` constraint keeps
headers, actions, and content visually connected while leaving enough room for
ordinary forms and multi-section content.

### Use Compact for Focused Tasks

Use `compact` when the user should concentrate on one narrow task, such as
completing a short form, reviewing a confirmation, or moving through a setup
step. It uses `max-w-2xl`, leaving enough room for ordinary form groups without
making a focused workflow feel like a full-width page. Avoid it for dense forms
that need several side-by-side fields or for content whose readability depends
on horizontal space.

### Use Full Width Deliberately

Use `full` when additional horizontal space directly improves the task, such as
comparing table columns, scanning dashboard panels, working on a canvas, or
using a split view. Full width removes the content max-width constraint, but inner
content should still define its own readable width where necessary.

Combine `PageContent` with [Page Layout](/docs/layout/page-layout) when a full or
default page needs responsive primary or secondary sections. Do not switch
`Page` variants at breakpoints merely to make the page responsive; use the
content layout and its container queries for responsive structure.

## Accessibility

The breadcrumb navigation, ancestor menu, and more-actions labels use the `page`
resources in the `thread-ui` i18next namespace provided through `AppProvider`.
Override them with `BreadcrumbActions`'s `aria-label` and `menuLabel`, and
`PageActions`'s `secondaryMenuLabel`. Each `BreadcrumbAction` uses its children
as its accessible name; an explicit `aria-label` takes precedence.

## Breadcrumb navigation

Place `BreadcrumbActions` inside `PageHeader`. Compose `BreadcrumbAction`
children in order from the outermost ancestor to the nearest parent; the current
page belongs in `PageTitle`. Arrays, conditional children and fragments are
supported. Place the action components directly in this container, rather than
hiding them inside a custom wrapper component.

- No actions: the navigation renders nothing and occupies no header space.
- One action: an arrow links directly to the parent, with the target's name
  available to assistive technology and on hover.
- Multiple actions: an ellipsis button opens a menu containing every parent,
  with a chevron separating the control from the title.

```tsx
import Link from "next/link";

<BreadcrumbActions>
  <BreadcrumbAction render={<Link href="/products" />}>
    Products
  </BreadcrumbAction>
  <BreadcrumbAction render={<Link href="/products/123" />}>
    Acme Widget
  </BreadcrumbAction>
</BreadcrumbActions>;
```

Use `render` for framework links, or `onClick` for application navigation. Both
an element and a Base UI render function are supported; custom render functions
must forward the supplied props and ref. A custom render defaults to a non-button
link; set `nativeButton` when rendering a native button. The component does not
infer routes or call browser history. It replaces the removed `PageBackAction`.

Navigation, title, and page actions share the first row at every screen size.
The title takes the remaining width and truncates to one line with an ellipsis;
its full text remains available to assistive technology. All responsive behavior uses the
`@2xl/page` container breakpoint (42rem / 672px of Page content width). Below it,
titles use a smaller font size and descriptions span the full header. At and
above it, descriptions align with the title and extend to the right edge.
Descriptions wrap naturally on the second row. Omitted navigation and actions leave their space
available to the title.

## Previous and next items

Place `PagePagination` after the primary action inside `PageActions`. It uses
shadcn `ButtonGroup` with two secondary icon buttons to navigate between resource
details, such as products or orders. The caller supplies navigation and disables
unavailable directions; this does not paginate a table.

```tsx
<PageActions>
  <PagePrimaryAction onClick={save}>Save</PagePrimaryAction>
  <PagePagination>
    <PagePreviousAction disabled={!hasPrevious} onClick={goToPrevious} />
    <PageNextAction disabled={!hasNext} onClick={goToNext} />
  </PagePagination>
</PageActions>
```

The group is hidden below 672px of **Page content width**, matching the breakpoint
for inline secondary actions, title size, and description alignment. Narrow
containers use the compact presentation even on a large screen. Hidden controls
are excluded from keyboard focus. Visible controls
use normal Tab navigation. Their default labels are localized; override
`aria-label` for resource-specific names.

Buttons default to `type="button"` to avoid submitting an enclosing form. Use
Base UI `render` for framework links, forwarding props and ref in custom render
functions. Set `nativeButton` when a custom render returns a native button.

```tsx
<PagePagination>
  <PagePreviousAction
    aria-label="Previous product"
    render={<Link href="/products/123" />}
  />
  <PageNextAction
    aria-label="Next product"
    render={<Link href="/products/125" />}
  />
</PagePagination>
```
